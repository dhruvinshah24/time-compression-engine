## 1. Cycling Event Findings (OBS-001)

### What was found

All 129 cycling events were generated by **`narrative_builder`** (Pass 7 of S07). This is not a detection rule — it is the activity classifier reading `track_activities` populated by `ActivityClassifier.classify()`.

One cycling event is generated per confirmed person track, where `ActivityClassifier` returned `label="cycling"`. 129 events = 129 unique tracks = **83.8% of confirmed person tracks** classified as cycling.

### Why ActivityClassifier classifies most persons as cycling

Source: [`activity_classifier.py`](file:///C:/Users/dhruv/.gemini/antigravity/scratch/time-compression-engine/backend/app/utils/activity_classifier.py) — `_detect_cycling()`.

Two signals:

**Signal 1 (bicycle proximity):** Returns cycling_conf ≥ 0.70 if person centroid is within 25% of frame from a bicycle track. One bicycle track confirmed — some persons near it may get this signal.

**Signal 2 (velocity + height stability):** Returns cycling_conf = 0.65 if:
- `mean_speed >= CYCLE_HORIZ_THRESHOLD (0.018 normalized units/sec)` AND
- `height_std < 0.03 normalized units`

At archive_001 parameters (320×240, frame_skip=5, fps=30):
- `CYCLE_HORIZ_THRESHOLD = 0.018 normalized/s = 5.76 pixels/sec = ≈1 pixel per extracted frame`
- `height_std < 0.03 = 7.2 pixels variance in 240px-tall frame`

**Any person who moves more than ~1 pixel per extracted frame with reasonably stable detection size will be classified as cycling.** For small/distant persons on a 1948 street (stable small bboxes, normal walking pace), both conditions are trivially met.

### Cycling sample audit

20 events sampled across the 300-second interval. All: **NOT VERIFIABLE** — no ground truth annotation, no frame-level inspection conducted in this phase.

Observations:
- 6/20 have `cycling_conf=0.65` exactly → Signal 2 fired (velocity-only path)
- Several tracks have duration < 1s — insufficient for cycling classification
- mean_speed ranges from 0.035 to 0.371 normalized/s — spans both walking and fast-moving persons
- No frame-level evidence distinguishes cyclists from pedestrians

### Manual audit false-event rate

**NOT CALCULABLE.** No CORRECT/FALSE classifications were made. Footage not watched at frame level in this phase.

### Cycling root cause determination

**Cause B (cycling rule over-triggers) — LIKELY, not confirmed.**

Evidence for over-triggering:
- 83.8% of persons classified as cycling is implausible for a pedestrian safety film
- `CYCLE_HORIZ_THRESHOLD = 0.018` is calibrated for 848px indoor footage, not 320×240 outdoor
- Multiple tracks with duration < 1s classified as cycling — insufficient observation length
- Temporal distribution: 50/129 events in final 60s — likely tracking fragmentation inflating count

Evidence against: Archive_001 is a 1948 street scene. Cyclists are plausible. We cannot rule out genuine cycling without watching the footage.

**Final status: NOT YET DETERMINED.** Requires watching at least 5 clips for the longest-duration cycling tracks (1, 15, 490) before making a determination.

## 2. Story Failure Findings (FAIL-008)

### What was found

**Root cause 1 (PRIMARY):** `cycling` is not in `_ACTION_EVENTS` in [`story_builder.py`](file:///C:/Users/dhruv/.gemini/antigravity/scratch/time-compression-engine/backend/app/engines/temporal/story_preservation/story_builder.py).

```python
_ACTION_EVENTS: frozenset[str] = frozenset({
    EventType.PERSON_WALKING,    # "person_walking"
    EventType.PERSON_RUNNING,    # "person_running"
    EventType.PERSON_STANDING,   # "person_standing"
    EventType.PERSON_LOITERING,  # "person_loitering"
    EventType.VEHICLE_APPROACHING, EventType.VEHICLE_RECEDING, EventType.VEHICLE_STATIONARY,
})
```

`cycling`, `running`, `walking_upstairs`, `walking_downstairs`, `person_sitting`, `person_crouching_sustained`, `person_fallen`, `person_crawling`, `person_reaching_up` are all absent.

**Root cause 2 (SECONDARY — type mismatch):** The narrative builder (Pass 7) emits `event_type = "running"` but `_ACTION_EVENTS` contains `"person_running"`. These strings do not match. Running events cannot qualify as ACTIONs.

**Root cause 3 (SECONDARY — state machine):** The activity state machine emits `person_entered_scene` and `person_left_scene` but does not emit a `person_walking` event for the walking state. No confirmed person track has a `person_walking` event in the 300s output.

### S08→S09 event count integrity

**No events lost.** All 232 S07 events pass through S08 and reach S09 intact.

### Story candidate chains

148 story segments. All PARTIAL, MINIMAL, ENTRY_ONLY, or EXIT_ONLY.

**10 tracks would be COMPLETE if cycling were added to `_ACTION_EVENTS`.**

Representative canonical pattern:

→ S09: PARTIAL (entry+exit, no action)

## 3. OBS-003 Investigation

**Segment:** `seg_1_e9932991`, Track 1, 12 events, 5 continuity issues.

**Finding: Genuine defect in `ContinuityChecker`.**

Track 1 events:
```
00:00  person_reaching_up     (narrative_builder)
00:01  person_entered_scene   (activity_state_machine)
00:01  cycling                (narrative_builder)
00:08  person_reaching_up
00:11  person_reaching_up
00:13  person_left_scene      ← TERMINAL EVENT set here
00:16  person_reaching_up     ← issue: follows terminal
00:21  person_reaching_up     ← issue
00:27  person_reaching_up     ← issue
00:41  person_reaching_up     ← issue
00:48  person_reaching_up     ← issue
00:53  person_reaching_up     ← issue
```

`person_left_scene` at 00:13 sets `seen_terminal=True` in `ContinuityChecker`. Events 7–11 (`person_reaching_up` at 00:16–00:53) are flagged as continuity violations.

**Why do events exist after the exit?**

The narrative builder generates events for the full track observation window. Track 1 is observed from 00:00–00:53. `person_left_scene` is generated by the state machine when the person reaches an edge (00:13), but the tracker continues following the person until 00:53. Narrative events cover the full span regardless.

**Is OBS-003 related to FAIL-008?** No. Track 1 is PARTIAL regardless of the continuity issue (cycling not an action). The continuity issue reduces its narrative score but does not determine completeness.

**Classification: Genuine StoryBuilder defect** — low severity. Only 1 segment affected in 300s run. Does not block production use but should be fixed before 24-hour validation.

## 4. Recommended Fixes

No fixes implemented in Phase 6C. The following are diagnostic recommendations only.

### Fix 1 — Add activity labels to `_ACTION_EVENTS` (story_builder.py)

**Priority: HIGH. This is the primary cause of FAIL-008.**

Add to `_ACTION_EVENTS`:
```python
"cycling", "running", "walking_upstairs", "walking_downstairs",
"person_sitting", "person_crouching_sustained", "person_fallen", "person_crawling",
"person_reaching_up",
```

**Expected effect:** 10+ tracks immediately become COMPLETE. Additional tracks may become complete if `running`, `person_sitting` etc. qualify.

**Risk:** LOW. This is a vocabulary extension. It cannot reduce existing complete stories (there are none). It can only create new COMPLETE classifications where PARTIAL previously existed.

**One-line test:** Run S09 on existing Phase 6B events with updated `_ACTION_EVENTS`. Count complete segments before deploying.

### Fix 2 — Align narrative builder event type strings (activity_classifier.py or story_builder.py)

**Priority: MEDIUM.**

Pass 7 emits `event_type = activity.label` where `activity.label = "running"` but `_ACTION_EVENTS` uses `EventType.PERSON_RUNNING = "person_running"`.

Fix A: Add `"running"` to `_ACTION_EVENTS` (covered by Fix 1 above).
Fix B: Change Pass 7 to emit `"person_running"` when `activity.label == "running"`. This creates semantic consistency.

Fix A is simpler. Fix B is cleaner long-term.

### Fix 3 — ContinuityChecker terminal event scope (continuity.py)

**Priority: LOW.**

`seen_terminal` check should not flag events from different generators (narrative builder) that are generated retrospectively over the full track span. The check should either be limited to state-machine events or should verify that the event generator was time-bounded by the exit event.

**Smallest evidence-supported fix:** Allow narrative events (rule_name="narrative_builder") to follow terminal events without triggering a continuity issue. Or: clip narrative events to the exit event timestamp in Pass 7.

### Fix 4 — Cycling calibration (activity_classifier.py)

**Priority: MEDIUM — but requires footage inspection first.**

`CYCLE_HORIZ_THRESHOLD = 0.018` is miscalibrated for 320×240 footage.

At 848px (original calibration): 0.018 × 848 = 15.3px/s.
At 320px (archive_001): 0.018 × 320 = 5.76px/s = ~1px/frame.

Consider: either frame-resolution-adaptive threshold, or raise the threshold substantially, or require minimum observation count (e.g., ≥ 10 frames) before classifying as cycling.

**Do NOT change this threshold until footage inspection confirms false positive rate.**

## 5. Final Answers

**Q1: Is cycling dominance caused by real footage or a rule problem?**

**Leaning toward rule problem** (Signal 2 threshold miscalibrated for 320×240 outdoor footage) but NOT CONFIRMED. Footage inspection required before changing the threshold. The 1948 street film plausibly contains cyclists but 83.8% classification rate is implausible for any footage.

**Q2: Why are there zero COMPLETE stories?**

`cycling` — the dominant event type (55.6% of all events) — is not in `_ACTION_EVENTS`. Tracks with `person_entered_scene + cycling + person_left_scene` are classified PARTIAL instead of COMPLETE. This is the primary cause. Verified by exact event-chain tracing on 10 candidate tracks.

**Q3: Is FAIL-008 a genuine StoryBuilder defect?**

**YES.** `_ACTION_EVENTS` was defined without including the event types that `ActivityClassifier` (Pass 7) actually emits. This is a vocabulary mismatch between the classifier output and the StoryBuilder completeness logic. Additionally, `"running"` ≠ `"person_running"` is a type-string mismatch.

**Q4: Is OBS-003 related to the same root cause?**

**NO.** OBS-003 is caused by `ContinuityChecker` flagging narrative events that occur after a terminal event (`person_left_scene`) in the same long-running track. Different root cause. Low severity.

**Q5: What is the smallest evidence-supported fix?**

Add `"cycling"` to `_ACTION_EVENTS` in `story_builder.py`. Single-line change. Predicted effect: 10 tracks immediately become COMPLETE without any other code changes. No regression risk (there are no existing complete stories to break).

This is the minimum intervention for Phase 6D.

**Q6: Are we ready for the 595-second run?**

**Not yet.** The following should be resolved first:

1. **Fix 1 must be applied and verified** (add `cycling` to `_ACTION_EVENTS`). Running 595s with 0 complete stories produces no new signal about story quality.
2. **OBS-001 cycling root cause** should be inspected at frame level for at least 5 clips before the 595s run, to understand whether the dominant event type is meaningful or noise.

If both are addressed, the 595s run will produce meaningful complete-story counts for the first time.
